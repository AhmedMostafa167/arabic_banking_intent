# Lessons log

Newest first: `YYYY-MM-DD · <area> · <what broke> → <root cause> → <how to spot it next time>`

- 2026-11-01 · tracking · one `register_model.py` call created two registry versions (v2 and v3) of the same run → the single-worker MLflow server was busy receiving a 270 MB model upload, the client timed out after 120 s and retried, and the first request had already succeeded → don't register while a large upload is running; after any registration, list the versions and check there is one per run.
- 2026-11-02 · serving · the ONNX model in a 3-CPU container used 2 CPUs for one request, and 2 users waited 3.7 s at the median → ONNX Runtime sizes its thread pool from the host's cores (4), not from the container's CPU limit, and its idle threads busy-wait → set the threads per request explicitly (`INFERENCE_THREADS`, at most the container's CPUs; 1 was best here) and load-test inside the container, not only offline.
- 2026-11-02 · benchmarks · offline, ONNX looked 3-4× faster than PyTorch; served, it was 25-40% faster at the median → the offline PyTorch timing ran while the laptop was swapping, and serving adds HTTP, the CPU limit and concurrency → decide on served numbers, and correct any note written from offline ones (v7's registry note was rewritten).
- 2026-11-02 · onnx · both int8 rungs failed to build ("Unable to find data type for weight_name=…MatMul_output_0"; "Incomplete symbolic shape inference") → quantisation needs every tensor's type, which the fused graph's custom operations (Attention, SkipLayerNormalization) hide, and ONNX Runtime's symbolic shape inference gives up on dynamic batch and sequence sizes → quantise the plain fp32 graph after `quant_pre_process(..., skip_symbolic_shape=True)`.
- 2026-11-02 · benchmarks · the graph-optimised model looked 60% slower than the plain one, and the thread sweep was non-monotonic (3 threads slower than 1, 2 and 4) → they were timed while swap was full (4.0 of 4.0 GB) → time all variants back to back in one run on a quiet machine, and read `free -m` before trusting a timing.
- 2026-11-02 · onnx · the build script printed its last line and then kept running at 200% CPU for hours → it never exited; by all signs ONNX Runtime's busy-waiting worker threads kept the process alive → log each result as soon as it exists, so a process that never exits loses nothing, and stop it once its results are in MLflow.
- 2026-11-02 · shell · `pkill -f <pattern>` killed the shell running it, three times → the shell's own command line contained the pattern → stop processes by PID, or put a multi-step chain in a script file so the pattern is not in any command line.
- 2026-11-01 · registry · after `ml/` became `training/`, registered v4 failed to load with `ModuleNotFoundError: No module named 'arabic_banking_intents.ml'` → a wrapper logged as an object is pickled by reference to its module path → log wrappers as code; re-log old versions (`scripts/relog_model.py`) before moving their module.
- 2026-11-01 · docker · the MLflow container never became healthy: its health check timed out while the container used 939% CPU and 1.3 GB → MLflow 3 servers start a job runner and 6 huey workers (GenAI online scoring, unused here), each importing MLflow; with no `start_period`, failures during that slow startup used up the retries → set `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false` (the server then needs 390 MB) and give health checks a `start_period`; `docker top <container>` shows what a container is running.
- 2026-11-01 · docker · `docker compose up --build` failed with "lookup ghcr.io: no such host" while `getent hosts ghcr.io` in WSL resolved it → Docker Desktop's network is intermittent here (a base-image pull also timed out, then worked) → retry before changing anything; `docker pull` the base images once so later builds use the cache.
- 2026-11-01 · tests · the test suite took 199 s instead of about 12 s, and importing pandas alone took 44 s → the WSL machine was out of memory (75 MB free, 1.8 GB in swap; VS Code and its extensions held about 2.5 GB), so library files were read back from disk → check `free -m` before timing anything on this laptop; `python -X importtime` shows where import time goes.
- 2026-11-01 · tracking · a failed re-log marked the champion's training run as FAILED → `with mlflow.start_run(run_id=<an existing run>)` ends that run as FAILED when the block raises (and gives it a new end time even when it succeeds) → when reopening a finished run, end it with `mlflow.end_run()` in a `finally`; check the run's status after any failed logging.
- 2026-11-01 · tracking · `log_model(..., metadata={ModelMetadataEnum.INTENT_NAMES: ...})` failed with `yaml RepresenterError: cannot represent an object` → MLflow writes metadata into the `MLmodel` YAML file, and the YAML writer matches exact types, so a `StrEnum` member is rejected although it is a `str` → write `.value` into anything serialised; test with the real enum, not a string literal (the earlier test used `"intent_names"` and passed).

- 2026-11-01 · tracking · logging each AraBERT run took about 15 minutes and pushed the 4 GB WSL machine 3.4 GB into swap → the consistency check runs the model over 2,397 validation texts on a slow CPU, and `mlflow.pyfunc.log_model` loads the model again to infer the signature from `input_example` → budget about 15 minutes per BERT-size model on this laptop, close other programs first, and check `free -m` if a step slows down.
